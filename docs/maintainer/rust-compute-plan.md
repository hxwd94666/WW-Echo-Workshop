## 阅读摘要与本次交付边界

2026-10-18 定向验收复现了匹配缓存下标、异步确认意图与筛选勾选恢复三项回归，匹配展示的业务排序仍有 Python 残留。接下来的批次、规模判断与最小验证安排见 [验收后续开发计划](rust-compute-follow-up.md)；本总体方案的全部需求和完成门槛继续生效，不因修复三项问题就缩小为局部交付。

本方案同时推进两条主线：**改进搜索质量与有效计算比例**，以及**将全部业务求值收口到独立 Rust 计算程序**。语言迁移解决执行成本，搜索策略解决“预算耗在错误方向”；仅完成其中一条不算完成需求。

- **迁移范围**：评分、评级、匹配、配装、约束/目标、替换、差异、库存业务筛选/排序/统计、自定义权重及保存前业务验证。跨目录追踪调用，不只迁移 `core/`。
- **唯一后端**：切换后删除对应 Python 求值器；Rust 故障不给 Python 后端兜底。只有合理批处理后仍收益为负、且有同机端到端证据的具名微计算，才进入豁免清单；目前没有已批准豁免。
- **删除边界**：删除淘汰算法、入口、旧格式兼容和相关失效测试；玩家原文件、现行冻结历史、预留保护和事务恢复证据保留。
- **宿主边界**：只调整本插件；独立 EXE、后台通信、资源限额、有界取消和回收。不改 OKWW 源码、依赖或启动设置，不将 Rust DLL 装入宿主。
- **交付门槛**：数值一致、方案质量、端到端性能、真实 OKWW 响应与故障存活分别验收；未通过就继续修复，不把“Rust 已编译”当作完成。

## 1. 最终要求与优先级

本方案采用用户最新补充的要求，替代此前“只迁移配装求解、保留 Python 评分和旧版本兼容”的建议：

1. 匹配、配装、单件评分、评级、替换预览等业务计算统一迁入 Rust。微小计算只有经过端到端测量证明留在 Python 更合适，才可列入明确豁免清单。
2. 不开发旧版本兼容、旧格式迁移、旧算法回退和双计算后端；淘汰代码核查调用后直接删除，不另存一套退休实现。
3. OKWW 仅作为宿主，不改其源码、依赖、解释器设置、进程优先级或加载机制。改动限定在本插件源码、开发工具和构建产物。
4. Rust 计算采用独立进程隔离，界面非阻塞、资源有界、故障可回收。宿主响应与存活是发布硬门槛，而非“用了 Rust 就自然满足”的假设。
5. 优化搜索效率与结果质量，不以语言迁移为由改变评分公式、目标比较顺序和现行五件约束。

删除旧版本支持指删除程序中的兼容实现，不等于删除玩家库存、截图、历史文件或事务恢复资料。现行功能需要的冻结快照、保护和提交恢复机制继续保留。

### 1.1 需求与验收对应

| 用户要求 | 实施约束 | 完成证据 |
| --- | --- | --- |
| 匹配、配装等所有计算迁入 Rust | 全调用链登记；同一业务只留 Rust 求值；微计算须端到端测量后具名豁免 | 迁移清单、入口测试、Python 残留审计和豁免测量 |
| 不做旧版本兼容，删除淘汰代码 | 调用方切换后删实现、配置和退休测试；无旧政策求值、兼容读取器或 Python 回退 | 删除映射、引用检查、当前格式回归；旧文件原件不变 |
| 不改宿主，避免计算拖死 OKWW | 仅改插件；独立 EXE、后台通信、资源限额、有界取消与退出 | 宿主源码/依赖改动为零；实际宿主心跳、故障注入和生命周期报告 |

插件自身的 `adapters/okww/` 可调整提交和回收逻辑；OKWW 安装目录的源码、依赖与启动配置均不在修改清单。宿主稳定性作为发布门槛，不以语言迁移或独立进程的存在代替实测。

### 1.2 开发效率与验证范围（执行约束）

1. **只保留必要验证**：围绕本次改动的明确风险选择最小验证集合；已有证据的输入、实现和环境仍有效就直接复用。避免反复基线/新版/安装包对照、重复打包和回退演练，不为每个小改动额外搭建验证框架或生成大批记录。必须保留的证据集中记录一次。
2. **测试只跑相关项，不跑全量**：优先指定具体用例，其次受影响模块；新增故障或跨模块影响出现时，说明原因并只扩大到有关调用链。不默认运行整个计算目录、仓库全套或完整性能矩阵，也不因阶段结束、收敛或发布准备自动扩大。全量测试仅在用户另行明确要求时执行，先前“请求默认同意”不视为该项明确要求。
3. **按改动类型选择**：文档仅核对修改内容和必要引用；纯输入投影改动验证身份/字段失效及对应结果；协议改动验证相关消息/取消路径；算法改动保留受影响的黄金样例与小型独立穷举。静态检查限定改动文件或受影响计算 crate，不搭便车检查无关模块。
4. **性能测量有明确问题才展开**：先用少量样本定位瓶颈，必要时再对当前优化入口测足样本；不在每轮开发重复全部规模/角色组合或正式 P95 矩阵。正确性、取消、数据原子性和宿主隔离所需的关键检查继续保留，不以减少验证掩盖回归。

本节优先于下文按阶段扩大验证的旧安排。最终验收按累计的相关证据核对需求；未覆盖项明确保留，不把一次全量运行作为开发或收敛的默认动作。

## 2. 已知事实与待验证事项

### 2.1 现有调用路径和前期合成测量

- 前期配装在同进程 Python 后台线程运行；现已由独立 Rust 进程执行搜索，下列旧测量仅作为改进前的定位资料。
- 五角色共享 25 件合成候选、目标均为 150：300 节点返回 170/150/150/150/140；2000 节点找到五人全达标方案。
- 五角色共享 300 件、43311 的合成案例：约 0.013 秒首次全达标，20 万节点总耗时约 4.8 秒，最终仍为节点受限。
- 对该 300 件案例的 2 万节点剖析中，上界计算链约占 68% 累计时间；其内部包含目标比较，比例不作重复相加。
- 仅在独立测试进程中优化整数比率比较，三轮各 5 万节点的中位耗时由 1.043 秒降到 0.767 秒；4000 次目标比较及该搜索样例对照通过。生产源码未应用该原型。

上述时间为前期记录，本次文档修订未重新执行性能测试，仅用于确定优化方向，不代表真实库存、所有场景或 Rust 收益。开发 P0 必须将输入、种子、环境、命令和输出固化成可重复基准；缺少对应原始记录的数字须补测，不把本节摘要当作完整性能证据。

### 2.4 已暴露的性能短板

现行性能文档已有同机探索记录：1500 件×8 角色、关闭结果缓存，原 Python 门面中位约 156 ms，Rust 路径优化后约 345 ms；该入口端到端尚有退化。配装差异中无当前方案的路径也存在新增通信成本。本次未重测，数字仅引用仓库现行性能说明，不作为正式 P95 或宿主验收。

## 3. 迁移边界：全部业务计算，而非仅配装

| 业务范围 | 迁入 Rust 的内容 | Python 保留职责 |
| --- | --- | --- |
| 单件与实时评分 | 主副词条贡献、技能权重、属性适配、逐项截断、当前分及现有潜力值计算 | 取得识别记录和冻结模板、提交异步请求、展示 |
| 单件和五件评级 | 阈值生成、边界比较、五件评级展示口径 | 读取冻结资料、颜色与文本绑定 |
| 批量匹配 | UUID×角色/玩法评分矩阵、适配判定、槽位/固定件匹配、排序所需业务键 | 管理独立要求和候选范围、缓存生命周期、分页展示 |
| 配装检查 | COST、槽位主词条、固定件、套装件数、同名、可用性和保护冲突的业务判断 | 构造快照、接收错误、控制显式运算动作 |
| 配装搜索 | 候选构造、目标比较、上界、剪枝、种子、重分配、预算及优先级组 | 作业生命周期、结果身份校验、展示与显式保存 |
| 已保存配装单槽替换 | 其他四件固定的候选评分、合法性、分差及新总分/评级 | 选择来源、预览上下文与原子提交 |
| 配装差异 | 保留/换入/换出集合、同 COST 展示配对、分差和评级差异 | 读取新旧冻结证据、渲染 |
| 库存业务筛选和统计 | 可批处理的筛选谓词、词条档位、业务排序键、汇总统计 | 收集筛选输入、模型行映射、视图状态 |
| 保存前计算验证 | 现行策略目标重算、配装约束与评分证据校验 | schema/字段类型校验、修订/事务检查、文件与数据库写入 |

盘点不限于 core：还要追踪 application、storage、resources、capture、ui 内残留的评分、排序、阈值、分差和约束计算，逐项标明新归属。存量函数名不是豁免理由。

下列操作按职责继续由 Python 承担，不建立 Rust 的重复 I/O 系统：Qt 布局/绘制、事件路由、协议序列化、数据读写与原子事务、日志、缓存身份、schema 结构检查、宿主接口调用。普通长度检查、UI 显示格式化等是否保留，须在盘点中明确，不以“所有机器指令都属于计算”扩大到重写界面或存储。

OCR 引擎、截图、图像编解码和宿主已有识别能力不在本次业务求值器重写范围；插件自有数值判定如参与评分或匹配，仍按上表迁移。已淘汰的养成分析、独立替换对比等功能不恢复。

### 3.1 微计算豁免门槛

每项豁免至少记录：调用入口、业务用途、输入规模、调用频率、Python 耗时、Rust 热进程批量路径端到端耗时、冷启动影响、P50/P95、方案取舍与测试。

- 先尝试批处理、缓存不可变标准或随已有请求返回，避免用“一次进程启动”与“一个加法”作失真比较。
- 数据转换、排队和通信成本必须计入；单独测 Rust 函数耗时不够。
- 仅当合理集成后收益仍为负，才保留微小 Python 运算。
- 维护一份明确清单；未列入清单的业务计算按迁移处理。
- 豁免不允许保留完整 Python 评分器、匹配器或搜索器作为备用后端。

每项计算登记至少包含：`入口/调用方 → 当前模块 → Rust 操作 → 输入/输出合同 → 删除项 → 黄金/穷举测试 → 热/冷测量 → 状态`。状态分为待迁移、已接通待验证、已验证待删除、已收口、具名豁免；文件存在、调用已改或测试暂过均不自动等同于已收口。普通 schema 检查、文本索引准备和日期解析也要标明职责，参与候选选择或业务排序的规则仍计入迁移清单。

## 4. 架构与代码组织

```text
Qt 页面 / OKWW 薄入口
          │ 显式动作，主线程仅提交和展示
Python application：快照、任务、异步协议、版本检查、故障处理
          │ 有界管道；不传数据库连接或宿主对象
echo-workshop-compute.exe
          ├─ 交互计算 lane：批量评分、匹配、筛选、替换与验证
          └─ 搜索 lane：配装、邻域改善、最优性搜索
          │ UUID / 分数 / 评级 / 原因 / 统计 / 终止状态
Python application / storage：冻结结果 → 用户确认 → 原子保存
```

使用同一份 Rust 程序、同一个计算库，按需要至多启动两个工作进程，避免长搜索堵住单件评分。由插件 runtime 唯一持有，页面不各自启动 EXE。短计算按块执行并检查取消；过期交互任务合并或撤销，防止队列积压。

Rust 求值函数不依赖 Qt、OK Script、网络或玩家数据库；通信入口负责协议，计算模块只处理明确输入。Python core 保留必要模型和无 I/O 的结构定义，不导入进程管理；异步编排全部位于 application。

## 5. 跨语言数值与业务合同

### 5.1 评分和评级

- 保持现有 +25 主词条口径、角色/玩法权重、逐词条两位截断、累计和评级边界；潜力值不冒充当前分。
- 迁移初期逐项复现现行乘除顺序及截断修正。禁止擅自使用融合运算、快速数学或重排算式改变边界。
- Python 的 round 与 Rust 默认 round 不直接视为同义；明确舍入方式，针对二进制边界与半值建立黄金样本。
- 评分求值完成后用整数分通信和搜索；评级十进制阈值用明确十进制口径，不得把所有输入先粗略量化为分。
- 非有限数、负值及超范围输入按 schema 明确处理；Rust 汇总、乘积使用足够位宽和 checked 运算，溢出返回有类型错误。
- Rust 返回词条贡献、当前分、现有潜力字段、评级和标准身份，Python 不再重复求值。

当前原生数值边界按字段区分，以下均为百分位整数 cents（150 分对应 15000）：每词条贡献上限为 `10^14`，单件最多七项贡献为 `7×10^14`，五件累计为 `35×10^14`；目标上限仍为 `10^14`。聚合字段使用足够位宽，不拿单词条上限误拒绝单件或整套累计。五件展示评级先把大于 4995 的单件 cents 修约为 5000，再求和；其合法非负 i64 输入不因超过单词条上限而失去评级。这些限额约束通信与求值，不改变正常模板的分数、逐项截断或阈值。

### 5.2 同级组目标

严格按以下字典序最大化，不转成随意加权总和：

1. 正目标达标人数。
2. 正目标角色中最低的 `min(总分/目标, 1)`；无正目标时取 1。
3. 合法配齐五件的人数。
4. 正目标角色取 `min(总分,目标)`、零目标角色取真实总分的效用之和。
5. 真实总分之和。
6. 负换装数。

比率用整数交叉相乘比较并检查乘积范围。目标封顶只影响指定比较项，不截断展示分数。跨组冻结和后组固定件预留保持不变。

#### 170/140 案例的判定与固定回归输入

170 与 140 合计 310，高于两人的目标合计 300，但声骸是不可分割的五件组合，且不同角色权重、主词条、套装、固定件与保护可能不同；总分充足不是存在合法重分配的充分条件。开发时分开判断：是否存在合法改善、比较器是否偏好改善、搜索是否在预算内发现改善。

固定合成用例：25 件不同 UUID、不同名称的 COST 1 声骸；五角色同模板、同级组、每人目标 150；无固定件、锁、保护或套装限制，槽位均接收这些主词条。评分矩阵中，5 件各 34 分、15 件各 30 分、5 件各 28 分，所有角色对同件评分相同。

- 初始方案为 `170 / 150 / 150 / 150 / 140`，仅四人达标。
- 将第一人的两件 34 分与第五人的两件 28 分交换，得到 `158 / 150 / 150 / 150 / 152`；五人均合法达标，真实总分保持 760。
- 新方案在第一比较项就优于旧方案，与后续总分、换装次数无关；如果比较器未选它，属于目标实现错误。
- 比较器正确而限时搜索停在旧方案，属于搜索覆盖或预算分配问题；新增达标种子、双角色精确邻域和质量回归，不靠改评分或扩大预算掩盖。

该矩阵是隔离测试输入，不作为生产评分接口。另用真实评分模板构造集成用例，从单件评分到配装重验完整贯通。加入多角色循环交换、不同模板及确实不可达目标的反例，防止只修好这一种分布。

### 5.3 身份、冻结与保存

请求必须带明确角色/玩法 ID、物理 UUID、要求、固定件、锁/保护、候选范围、库存/配装修订、资料身份和 scope generation。资源更新不自动开始计算。

Rust 结果只形成候选证据，不写玩家数据。Python 校验结果 UUID、schema、请求身份和当前修订；需要业务重验时批量调用 Rust validate 操作，而不是再建 Python 公式副本。验证完成后，在既有事务边界再次核对修订并提交，避免异步重验期间发生状态变化。

现行格式下的历史查看仍使用自身冻结快照，不用当前权重补算；这属于现行功能，不是旧格式兼容。

## 6. 搜索算法优化

### 6.1 每节点成本

- UUID、名称、套装映射为密集索引；评分矩阵及候选用紧凑数组。
- 位集合/索引数组记录独占；增量维护分数、换装、套装计数和组目标。
- 预计算不可变条件和等价槽位，减少热循环分配、字符串归一化和全组重复汇总。
- 避免每个节点构造完整结果；只在改善和有界进度发布时生成快照。

### 6.2 初解与局部改善

- 稀缺槽位、强约束和冲突程度指导访问顺序；同时保留高总分和达标优先种子。
- 达标种子前置并获得预算，避免全部预算耗在追高分种子上。
- 对未达标角色和有余量角色做十件精确重分配，最多 252 种五件划分；每种划分还需检查具体槽位指派、主词条、固定件、套装、保护与同名约束，不得将“252”直接当成全部实际操作数。
- 两角色改善严格按全组原目标接受；仍不足时再评估三角色邻域或引入未占用库存的受限大邻域搜索。
- 邻域搜索与全局搜索共用预算；局部最优不标记全局最优。

### 6.3 剪枝与证明

- 对已占用 UUID、同一高分件重复计入槽位、剩余套装需求做更紧的保守上界和可行性检查。
- 强上界按需启用，测量剪枝收益与计算成本。
- 只有证明等价且包含全部评分/约束/归属语义时才消除对称；不按名字合并物理声骸。
- 不用 Top-K 硬截断候选获得虚假的完备性，也不将各角色独立最高分当作可同时取得的组合。
- 先做可重复的单线程 Rust；并行搜索在独立基准证明有收益后启用，限制总线程数，不默认占满 CPU。

达到目标不自动宣布搜索完成。记录首次合法解、首次全达标、最后改善和证明阶段耗时，区分“找到好方案”和“证明更优方案不存在”。

## 7. 通信、进度与故障隔离

### 7.1 协议

- 首版采用带长度前缀的 UTF-8 声明式 JSON；不用 pickle 或执行性数据。发送与解码在后台执行。
- 握手包含 protocol_version、engine_version、现行算法/政策和能力集；仅支持一个当前协议，不自动协商历史协议。
- 操作包括 score_batch、rating_batch、match_batch、filter_batch、allocate、replace_preview、loadout_diff、validate_allocation、cancel；共用一次冻结输入和按身份缓存的不可变数据。未声明的入口明确报错，不回退到旧计算器。
- 消息含 operation_id、request_id、generation、快照身份和序号；结果分块，重复、过期、截断与错序消息按明确状态处理。
- 初始协议上限：单帧 4 MiB、单请求累计 64 MiB、最多 8 个待处理请求；超限显式结束该任务，不默默裁剪候选。P0 若发现合法基准超限，先调整协议并补测。
- 当前实现采用唯一 v2 协议，不回退 v1；超单帧请求和结果按 512 KiB UTF-8 片段分块，最多 256 块，每块校验 request_id、总长、序号与末块标记，重组后再核验完整消息身份。握手核对相同限额。结果完整之前不发布；发送队列两帧、接收队列一个逻辑消息，不无限缓存分块。正常小消息仍为单帧，不额外拆分。
- 进度每个作业最多每秒 5 次，且可合并为最新状态；stderr 使用有界环形缓冲，默认 64 KiB，不通过无限排队阻塞宿主。
- stdout/stderr 持续独立消费；取消控制不能排在长搜索之后，Rust 控制线程设置原子取消标记，由计算分块检查。

### 7.2 宿主存活和响应要求

- 不将 Rust DLL 加载进 OKWW；不在宿主注入、补丁或 monkeypatch；不安装或替换宿主依赖。
- 启动插件随包的固定绝对路径 EXE，禁用 shell，隐藏窗口，不从当前目录或 PATH 猜测程序。
- 用 Windows Job Object 管理仅属于插件的子进程，关闭插件/宿主时回收；适配宿主已有 Job 限制，隔离建立失败时停止该计算入口，不转成宿主内执行。
- 计算进程不持有数据库连接、计划文件写锁和宿主句柄；不主动联网，不读截图，不获得任意路径读写任务。
- 所有启动、序列化、写管道、读管道、业务验证及等待回收均在后台；主线程禁止 wait/join/result 式阻塞等待。
- 退出时先拒绝新请求并使排队任务结束，再取消在途计算、关闭管道、后台回收子进程；输入准备函数也受截止时间与取消约束。后台执行器退出等待同样纳入检查，不能让线程池在宿主退出时无限等待。
- 控制 CPU 线程数、快照缓存和进程内存；初始内存硬上限交互进程 256 MiB、搜索进程 512 MiB。超限按故障处理并保留旧界面结果，实测后可经明确评审调整上限。
- 启动握手目标超时 3 秒；取消目标 250 ms 内反馈，1 秒内完成协作退出或启动强制回收。截止时间覆盖作业各阶段，宿主 watchdog 不依赖子进程自行报时。
- 区分搜索预算耗尽、用户取消、进程挂起、启动失败、协议错误与异常退出；预算正常耗尽可返回最佳方案，故障/取消不伪装成成功。
- panic、异常终止、输出阻塞、资源超限只使本次工作失败；不向宿主传播未处理异常。禁止无限重启；失败后只允许有限重建，新的计算需明确提交。
- 仅终止已持有句柄的计算子进程，不按模糊进程名结束 OKWW 或其他程序。

独立进程能隔离大部分计算崩溃，但不代替对资源耗尽、父进程读写和 GUI 发布的测试。不承诺未经实测的“任何环境永不崩溃”；以下故障注入和真实宿主门槛必须全部满足后再交付。

### 7.3 全链路非阻塞与提交边界

- 不只检查“点击计算”：runtime 初始化、切档案、历史读取、导入校验、保存重验、结果建模与关闭也逐项检查线程归属。启动阶段需要原生重验时，先展示加载状态，再后台完成装配；禁止在 Qt 构造函数内同步等引擎。
- runtime 显式注入共享计算服务给应用用例和存储验证边界，临时导入仓库、恢复副本也沿用同一依赖。不得为存储或页面另开第三个隐式引擎，不建全局单例补依赖。
- 读取冻结输入及修订 → 后台 Rust 重验 → 开启短事务/文件提交锁 → 再核对修订并原子提交。不得跨进程求值时长时间持有 SQLite 写事务；修订变化则拒绝本次提交并保留旧结果。
- 搜索、通信、输入准备、主线程结果模型构造分别设量级上限；大批结果分批发布，避免 Rust 已结束而 GUI 仍连续建卡片。两个 lane 的 CPU、内存和父进程缓存合并观测，不能仅限制子进程 RSS。
- Python 后台线程不等于主线程始终流畅：大对象构造、JSON 编解码与结果投影仍需单独计量其 GIL/事件循环影响。复用冻结模板、按有界批次准备和发布、减少跨语言对象数量；根据真实心跳定位停顿，不能仅凭线程名判定无阻塞，也不为规避该问题把 Rust 改成宿主内 DLL。
- 启动握手、输入准备和进程回收各自故障注入；底层进程创建 API 的等待与任务取消反馈分别计时，后台启动迟到的子进程仍须回收。明确区分“界面已反馈取消”和“进程已退出”。

存储重验现走交互队列并将正常取消映射为统一 OperationCancelled；归档、档案导入、恢复副本和修复服务均显式传递验证依赖。runtime 初始化失败也会关闭计算所有者；紧急修复在无 runtime 时可独立持有服务，有 runtime 时复用原所有者。

当前已将取消标记传入握手接收，并在进程创建返回后、业务发送前检查取消/关闭/截止时间；作业 watchdog 的反馈覆盖计算及启动等待。新增故障覆盖握手无输出、启动退出、错误版本、迟到返回三种终止原因及运行中死循环；原队列线程仍负责回收，不因 Future 结束无限启动新线程。分块传输新增错序、重复、身份、累计超限、截断及传输中取消检查；真实 OKWW 交互心跳、完整性能矩阵和其余工作包仍待完成。

## 8. 删除旧代码和格式支持

### 8.1 删除范围

- 被 Rust 接管的完整 Python 评分、评级、匹配、搜索、替换及业务校验实现。
- v1 目标政策求值、旧序列化读取、旧字段推断、旧预算回退及旧品牌/入口兼容分支。
- 仅服务退休功能的模块、配置读取、数据适配和测试；引用全部更新后删除，不用隐藏开关保留。
- 双后端选择、Rust 失败后退回 Python、同义模块转发和永久影子计算。

删除前查生产调用、导出接口、资源导入、保存验证和 UI 隐性调用；历史关联、保护 claims、事务意图与文件锁不是普通遗留垃圾。现行正常功能仍依赖的代码保留或迁入 Rust，不得一并删掉。

### 8.2 数据处理

- 只支持一个当前 schema/策略集合；当前格式未变的库存和历史继续按当前格式处理，不为迁移语言而强制改文件。
- 旧 schema、缺失旧字段和淘汰政策不自动升级、不猜测补齐，也不保留迁移器。检测到后明确说明格式不受支持并保留原文件，不清库、不静默重置成空档案。
- 不自动批量重写历史；新建档案必须是用户显式操作。
- 删除退休字段读取前核查它是否仍属于现行 schema。若确实需要调整现行格式，先定义唯一新 schema、界面提示及只在副本上的验证，不顺便制作旧格式适配层。
- 原版本包和数据备份可作为部署回退材料保存在安装扫描目录之外；不是新程序中的兼容模式。新格式数据与旧包之间不承诺互读，回退不自动覆盖任何玩家文件。

测试仅保留必要的“不支持旧格式时原件不变”断言；旧格式成功兼容测试随实现退出。评分、评级、约束及穷举的有效断言继续保留，不通过删失败测试掩盖迁移差异。

每阶段只运行改动相关测试，P4/P5 同样遵守第 1.2 节，不默认执行整个计算目录或历史 UI 全套。收敛核对累计证据和实际缺口，只补缺口相关验证；不自动安装到宿主、不提交、不推送、不打 tag、不正式发布。

### 9.1 生产切换的具体工作顺序

1. **运行时归属**：runtime 持有至多两个 worker；装配评分与配装门面，构造失败、切档案、关闭及卸载都走同一有界回收路径。
2. **评分和匹配**：切换快速评分、批量匹配、实时推荐与页面内隐性评分；缓存必须包含库存内容、角色/玩法、规则及冻结资料身份。大矩阵按块传输与发布，避免一次 JSON 或 GUI 建模卡顿。
3. **配装求解**：切换预检、评分矩阵、搜索和完整结果重验；生成方案 UUID、修订绑定与保存事务仍由 Python 编排。固定件与保护不得在序列化时丢失。
4. **剩余求值**：切换库存业务筛选/排序/统计、单槽替换、配装差异、存储入口的业务证据核验；逐项关闭 Python 求值入口，而非只改页面主按钮。
5. **同步删除**：每个入口通过数值与故障测试后，更新全部调用与导出并删除对应旧实现。测试辅助假数据仅存于测试，不允许生产代码按“测试环境”选择另一套计算器。
6. **收敛交付**：核对累计定向回归、残留审计及尚缺的构建/实际 OKWW/部署回退证据，只补必要且相关的缺口，不默认重跑计算目录全套；有未通过出口就保留明确缺口，不宣布全量迁移完成。

阶段记录至少提供“入口 → 原求值模块 → Rust 操作/模块 → 删除文件/字段 → 测试证据”映射；微计算豁免另列测量记录，避免以文件是否含 Rust 字样判断完成。

## 11. 性能与响应门槛

基准候选范围为合成 300/1500/5000 件、匹配 1/3/8 角色、配装 1/5/8 角色，以及资源充裕、候选高度重叠、稀缺套装、接近目标和已知无解等情形。日常只选与当前瓶颈有关的代表输入，先少量采样；不默认遍历全部组合。确需正式 P95 验收的相关入口才每组至少 50 次，保留原始样本及百分位算法，区分冷启动、热进程、缓存命中和带 profiler 运行；已有有效样本直接复用。GUI 心跳另记录连续时间序列，不以少量任务平均值替代事件延迟。

记录：读快照、准备、序列化、排队、评分、搜索、传输、GUI 发布时间；节点吞吐；首次合法解/全达标/最后改善；最佳目标曲线；峰值 RSS；事件心跳 P95/最大间隔；取消确认和回收耗时。

初始开发目标（待 P0 同机基线校准，均非现成承诺）：

- Rust release 配装纯求解中位吞吐至少达到当前 Python 基线的 3 倍；算法改动另按固定时间比较质量，不混用节点数冒称等价工作量。
- 300 件×5 角色可行基准的首个完整合法方案 P95 小于 1 秒；困难/无解案例单列，不套用存在性承诺。
- 1500 件×8 角色热进程匹配，端到端 P95 目标小于 500 ms；冷启动单独披露。
- 同规模匹配、评分、筛选等入口另与冻结的同机旧基线比较 P50/P95；先规定测量噪声容限，超出容限的持续退化记为未通过，继续合并请求和优化输入/输出。仅达到 500 ms 等绝对门槛，不足以证明比旧实现更快；具名微计算例外仍须满足第 3.1 节证据。
- 同时间预算的规定质量基准不低于当前实现；新的搜索顺序在任意未知输入上不作绝对质量保证。
- 真实 OKWW 中计算期间 GUI 心跳 P95 小于 100 ms、最大间隔小于 500 ms；测试期间不出现系统未响应判定或宿主退出。搜索、结果发布和关闭均覆盖。
- 取消反馈 P95 小于 250 ms，1 秒内协作退出或进入强制回收；持续无输出/超时/强制终止也维持上述界面响应门槛。
- 两个 worker 的内存、CPU 和缓存必须受第 7 节限额约束；重复测试不得持续泄漏。

若某项未达标，记录输入与原因并继续修复，不靠增大默认预算、放宽断言、删困难样例或隐藏进度来通过。

## 12. 构建、依赖与交付

- 固定 rust-toolchain、Cargo.lock 和最小依赖；用户运行不要求 Rust、Cargo 或新增 Python 第三方包。
- Rust release 构建后验证 Windows x64 目标、运行库依赖和相对资源位置；不修改宿主来补齐依赖。P0 如需其他架构，单独建立制品矩阵。
- 构建输出置于源码之外；Rust 源码在唯一业务目录，发行只带必要 EXE、协议清单和许可，不带 target、测试、源码缓存或开发工具链。
- 复用 `tools/build.py` 现有原生专用白名单：普通包成员仍限 .py/.json/.png，原生源码单独核验并生成 EXE 与清单；不得简单开放打包任意扩展名。现有链路继续补齐干净构建与安装根自检。
- 增加 EXE、协议清单、源码版本/构建标识与 SHA256 的对应验证，解包后启动自检；开发计算程序不从在线资料更新通道下载。
- 统一从现有唯一产品版本生成 manifest 和 engine 构建身份，不另维护一份手工产品版本。协议、计算政策和引擎实现版本分别表达各自含义。
- 锁依赖和 release 不等于二进制可复现；固定路径映射、时间和工具链条件，实测两次干净构建及 ZIP hash，记录差异来源。
- 必要许可和第三方来源集中保留；不随包发布玩家记录、截图、缓存和诊断原始数据。

最终交付：源码改动、计算迁移/微计算豁免/删除清单、插件测试包、精确验证记录、同机性能报告和可运行部署回退脚本。安装只在用户明确要求后进行，旧包置于宿主扫描目录之外，玩家数据原位保留。

交付回退只恢复程序包，不在新程序里保留旧算法。涉及数据格式变化时只在备份副本上演练，不对真实数据自动降级。

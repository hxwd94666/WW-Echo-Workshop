## 1. 工作量判断

本轮要求边界的集中交付为 `build/development/follow-up-b2-model-guard/`，该批次引擎为 rust-compute-19。`requirement_checks.rs` 的布局/主词条与套装规则已合入 `pin_check` 和 `match_batch`，故绕过 Python 构造器的非法要求也会被拒绝，不新增生产 RPC。匹配请求和缓存身份现在包含允许套装及件数要求，并冻结内层元组，防止可变要求原地修改后复用旧分数。独立 `requirements_check` 是后续批量迁移的边界，不是 Python 故障回退。本轮尚未删除 Core 规范化函数，也未将配置读取/输入模型改为纯结构构造；下一步需一起切换这些调用，保证编辑、导入和保存各边界不漏校验，不因已有 Rust 文件就提前宣布完成。

针对该迁移决策做了单入口探索：同机热进程各 40 次、交替执行，1/8/128 角色的 Python 规范化 P50 约 0.028/0.150/2.099 ms，独立原生请求约 0.172/0.281/1.573 ms。比较“旧 Python 规范化＋既有固定件请求”与“候选的仅原生合并校验”，P50 约 0.229→0.176 / 0.475→0.317 / 3.925→2.236 ms；原始 P95、单次冷启动与命令见同目录 `model-costs.json` / 复测脚本。候选流跳过 Core 的部分只在探针中执行，生产调用尚未完成这种删除；不把候选数字当成已实现提速。冷启动只测一次、两条路径不同，不能据此比较优劣。数据说明独立小 RPC 较慢不构成整项豁免理由，批量/合并仍有收益；目前仍没有新增微计算豁免。

**只修三项已复现问题，不是大工程；完成全部 Rust 化、性能优化和真实宿主验收，是中等规模收尾，不是重写项目。**

1. 业务源码只改 `src/echo_workshop/`；复用现有 Rust 引擎、runtime 双 lane 与后台服务，不建第二套后端，不引入 Python 计算回退。

6. **验证最小化，测试仅跑相关项，不跑全量。** 复用仍有效证据；不为每轮小改动重复打包、制作整套报告或回退演练。全量仅在用户另行明确要求时执行，“默认同意”不替代这一要求。

### A1. 匹配部分缓存命中下标错误

- 入口：`application/scoring.py` 的匹配响应回填，当前问题在第 301 行附近。
- 原因：`block` 是允许不连续的原始行号列表，`ids_native` 是紧凑批内列表；`index - block[0]` 不是可靠的批内序号。
- 改法：明确区分 `local_row = position // len(columns)` 与 `source_row = block[local_row]`。身份校验使用批内序号；缓存与矩阵回填使用原始行号。维持角色列映射、UUID 校验及整批发布，不用关闭缓存掩盖错误。
- 必要验证：把已复现的“先算中间一件，再算全部三件”断言纳入匹配相关测试；再以同一小样例覆盖多个角色列和分组缓存命中，不增加大库存矩阵。
- 出口：非连续缺失块正常返回，UUID/角色/分数顺序与无缓存结果一致；失败或取消不发布部分矩阵。

### A2. 延后确认必须保留原始操作意图

- 入口：`ui/shell.py` 的 `_finish_inventory_selection` / `_defer_filtered_selection`。
- 原因：等待视图后固定调用 `filtered=True`，丢失用户点击的 `filtered=False`。
- 改法：待确认请求显式保存确认类型、会话身份、档案、筛选代次和必要的调用方上下文。“确定勾选”冻结点击时确认的已选 UUID；“使用筛选结果”绑定对应筛选快照，不借用稍后另一个筛选结果。
- 生命周期：更换筛选、切档案、取消、换会话、调用页要求变化或筛选失败时撤销旧请求、断开回调并提示重新确认。重复点击只保留一个待确认，不排队多次应用。
- 发布：确认前重新核对会话与调用方上下文；不等待 GUI 线程，不把 `deferred` 当作已成功提交，不在等待期间改写候选范围。
- 必要验证：沿用已复现的“勾选 1 件、搜索匹配 4 件”用例；明确验证两个按钮分别提交 1 件与 4 件，再补一条取消/会话失效不续作的契约。
- 出口：操作意图不变、只提交一次，过期回调没有写入或导航副作用。

### A3. 异步视图发布后恢复可见勾选

- 入口：`ui/inventory/page.py`、`ui/inventory/cards.py`、`ui/inventory/filter_proxy.py`，以及库存模型发布路径。
- 原因：Qt 隐藏行时移除视图选择；新投影就绪只刷新提示，没有将会话保存的 UUID 恢复到重新可见的行。
- 改法：会话 UUID 是选择真值，Qt 选择仅是可见投影。投影变更期间抑制瞬时选择同步；按同一代次结果恢复当前可见已选 UUID、焦点和必要的滚动状态，再恢复通知与确认操作。未在视图中的已选 UUID 不清空。
- 等待/失败：筛选未就绪时不按旧行掩码确认或改写选择；禁用相关动作或明确延后处理。旧代次响应丢弃，失败保持原选择草稿并显示可重试错误，不走 Python 谓词兜底。
- 复用边界：共享卡片网格还用于替换与结果展示；只展示五件的无条件视图继续走结构性行映射，不为此额外启动筛选作业。共享组件的取消、关闭和重新打开沿用 runtime 所有权。
- 必要验证：保留“选 Echo-0 和 Echo-3 → 搜索 Echo-0 → 搜索 Echo-3 → 确认仍保留两件”的失败复现；结合一次有筛选的模型刷新验证恢复时序。不重新搭建整套界面测试。
- 出口：重新可见项正确勾选，确认不掉件，模型重置与过期响应不扩大/缩小已确认范围。

### A 的交付

修复源码、最少回归用例及一份集中记录；先把审阅目录里的三个失败复现转为稳定断言，纳入相关测试模块，不让长期测试依赖 `build/` 临时脚本。未触及算法的旧黄金/穷举证据可复用，不重跑整个计算目录。A 通过后再开展 B，避免性能优化掩盖功能错误。

## 4. 批次 B：完成剩余业务计算收口

### B1. 匹配展示代表项与排序迁入 Rust

验收时 `ui/matching/cards.py` 的 `_build_projection` 用 `max(...)` 选择代表角色、用 `entries.sort(...)` 进行业务排序。B1 已将其迁入 `native/compute/src/match_projection.rs`，原函数改为只映射结果的 `_map_projection`。以下方案现已接通并完成对应定向验证；不把 B1 的结果扩大为 B2/C/D 已完成。

推荐路径：

1. 复用已生成的冻结匹配矩阵，通过现有后台链路批量生成展示投影。可扩展匹配结果，或增加一个有界的原生投影操作；不要为每张卡、每次 Qt `data()` 调用发 RPC。
2. Rust 返回源行/角色引用、各角色及汇总视图的排序索引、排除/未知统计。Python 只按索引映射卡片和格式化标签，不再次比较分数或决定排名。
3. 大批次匹配合并后再确定全局顺序；不能直接拼接各分块内部排序。汇总代表项分数相同时保留当前选择顺序；展示排序同分按当前 UUID 规则打破平局，不顺带改变计算合同。
4. 结果绑定矩阵身份、库存与资料版本、角色/要求和显示范围；原生结果未就绪不发布半成品。取消/旧代次不覆盖新结果。
5. 切换角色只读取已有投影；不重新匹配库存，不回写角色配置，不把代表项误当独占分配。
6. 接通后删除对应 Python `max`、排序与业务统计循环；不保留隐藏回退。

必要验证只用小型冻结矩阵：多角色汇总、单角色、同分 UUID、排除与未知结果；核对旧合同中的顺序、代表项和统计，再检查 GUI 只做映射。无关评分公式与搜索测试不重复跑。

### B2. 按调用链确认其他残留与退休实现

复用总方案已有 W1–W5 清单，只更新已改变的入口与当前状态，不重新盘点已经有有效证据的所有模块。重点核对页面要求校验、库存业务判定/排序、保存前重验、资源/抓取中的数值求值及兼容读取器；业务求值迁入 Rust，schema、身份、事务、文件 I/O 与显示格式化留在 Python。

登记格式保持一张表：`入口 → 当前生产调用 → Rust 操作 → 删除项 → 必要证据 → 状态`。本次验收确认的匹配排序只是已知残留之一，不代表其余条目自动通过。微计算豁免仍须满足总体方案 §3.1 的具名端到端测量门槛；目前不新增豁免。

出口：每个保留的 Python 计算点都有明确职责或获批豁免，每个迁移项只有一个生产后端。删除前核对替代路径与现行历史/保护关联，不因删兼容误删恢复意图或玩家数据。

## 5. 批次 C：解决有证据的端到端性能短板

顺序是**定位 → 改最贵的一段 → 相关测量**，不是先改线程数或重写协议。

### C1. 匹配热路径

- 起点：性能文档记录 1500 件×8 角色热路径约 179 ms，旧门面约 156 ms；这些是既有探索记录，不是新的正式验收结论。
- 先复用现有分段计时，定位输入准备、缓存身份、编码/传输、Rust 求值、结果解码/模型构造与 GUI 发布的主要占比。已有列式单元与批处理继续使用。
- B1 完成后再决定是否合并投影请求、减少重复 `ComparisonScore`/评级对象构造或分批发布；不以裁掉仍被使用的字段换取速度，不放松 UUID/矩阵完整性校验。
- 先跑当前入口的少量同机样本；只有候选优化有效才补这一入口的 P50/P95 与内存证据。旧基线环境不一致时明确可比性缺口，不直接相减宣称提速。

### C2. 库存查询冷路径

- 起点：现有记录为 1500 行冷路径约 47 ms、热路径约 3–4 ms。热快照收益保留，先判断冷路径是否实际造成交互瓶颈。
- 若需要优化，优先减少完整载荷的重复准备/传输；紧凑或列式编码作为有证据后的选项，不为了文档里一个数字直接重写全协议。
- 保留完整字段身份、搜索文本口径、预留/状态语义和输入上限；不静默截断，不用 Python 求值回退降低延迟。
- 只测受影响的冷/热入口及快照变更；不展开所有库存规模×角色×模式的性能矩阵。

### C 的出口

达到总体方案的相关绝对门槛，并对冻结同机基线说明持续退化与噪声；1500×8 热匹配端到端 P95 目标小于 500 ms，不把低于该数当作已经比旧实现快。存在实质退化就继续定位，或按原方案审批具名微计算例外；不以“Rust 已运行”结束优化。

## 7. 最小验证与完成判定

- **文档改动**：只核对内容、引用和与现行约束的一致性；纯文档批次不运行代码测试、不构建安装包。
